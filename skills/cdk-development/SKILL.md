# cdk-development

Write AWS CDK infrastructure that a reviewer can trust. Not "code that synthesizes" — code whose
design, security posture and blast radius are deliberate.

## Guardrails — never violate

1. Never run a command that changes an AWS environment (`cdk deploy`, `cdk destroy`,
   `cdk bootstrap`, `aws cloudformation` mutations). Print it for the user.
2. Never decide a context-dependent question yourself. Ask, with options and trade-offs: removal
   policy, retention, public access, VPC placement, customer-managed keys, cross-account access,
   stack boundaries, IAM scope expansion, anything with data-loss potential.
3. Never weaken a security default or add a cdk-nag suppression to make validation pass.
4. Never embed secrets, credentials, access keys, account IDs the user did not give you, or profile
   names in code.
5. Never leave a validation failure unreported, and never work around one.
6. Never rename or restructure a construct that owns stateful resources without flagging that the
   logical ID change replaces the resource and can destroy data.

## Workflow

### 1. Understand before writing

- Read the existing structure: `lib/stacks`, `lib/constructs`, `lib/config`, `test`.
- Follow the conventions already in the repository (naming, folder boundaries, props style, test
  style) even where they differ from your preference. Say so once, then comply.
- Identify what the change actually needs: which resources, which environments, which data is
  persistent, what is exposed, who needs which permission.
- Ask about anything that is a project or business decision — before writing code, not after.

### 2. Design, and say why

State the design in two or three sentences before implementing: where the code goes, whether it is a
new construct or an addition to an existing one, and whether it belongs in the current stack.

- **Model with constructs, deploy with stacks.** Complexity goes into constructs. A stack is a
  deployment boundary (independent release, lifecycle, account, region, owner, blast radius,
  CloudFormation quota) — never a folder for a file that got long.
- Prefer L2 constructs. Use an L1 (`Cfn*`) only when the L2 cannot express the requirement, and say
  so in a comment.
- Extract a custom construct when configuration repeats, when a project standard or security policy
  needs one home, when several resources form one logical capability, or when a domain concept is
  worth naming. Do not wrap a single L2 construct in a pass-through class.
- Group code by domain or responsibility, never by AWS service.

See `references/construct-design.md`.

### 3. Implement with secure defaults

Default to private, encrypted, least privilege, logging where it helps, secrets in Secrets Manager or
SSM. Keep L2 secure defaults; do not override them for convenience.

IAM ladder — stop at the first rung that works:

1. `bucket.grantRead(handler)` — L2 grant API
2. `queue.grantConsumeMessages(handler)` — service-specific API
3. explicit `PolicyStatement` with concrete actions and ARNs
4. wildcard — only with a justification the user accepted

Never generate `Action: '*'`, `Resource: '*'`, `AdministratorAccess` or a broad managed policy as a
shortcut. See `references/iam-and-security.md`.

Pass values in through props. Do not read `process.env` / `CDK_DEFAULT_ACCOUNT` inside construct
code: it makes the template depend on whoever ran the command and breaks snapshot stability.

### 4. Test what you generated

Snapshot test per stack, always. On top of that, fine-grained assertions for everything generated
rather than written out: loops, conditionals, props-driven values, property overrides, security
properties (encryption, retention, public access, TLS), IAM statements you care about.

```ts
template.hasResourceProperties('AWS::SQS::Queue', { KmsMasterKeyId: Match.anyValue() });
template.resourceCountIs('AWS::SQS::Queue', 2);
```

See `references/testing.md`.

### 5. Validate and report honestly

```bash
<pm> run check     # format:check -> lint -> build -> test -> synth -> nag
```

Then report: what you built, why that design, what you validated with real results, which decisions
are still the user's, and the commands they should run themselves.

If cdk-nag reports a finding, present it — rule, resource, finding, security impact, recommended fix,
alternatives, trade-offs — and wait. If a snapshot diff shows a replacement, deletion, IAM expansion
or encryption change, present that too before touching the snapshot.
