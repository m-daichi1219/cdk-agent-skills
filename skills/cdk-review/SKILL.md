# cdk-review

Find what is wrong before AWS does. Report it with a recommendation — do not quietly rewrite the
user's infrastructure.

## Guardrails — never violate

1. Never run `cdk deploy`, `cdk destroy`, `cdk bootstrap` or any AWS mutating command. `synth`,
   `diff`, `ls` and the local pipeline are allowed.
2. Do not fix findings on your own initiative. Architecture, security, IAM and destructive change are
   always reported first and changed only after the user decides.
3. Never make a check pass by suppressing a cdk-nag finding, deleting or skipping a test, relaxing a
   lint rule, or updating a snapshot you have not explained.
4. Never report a clean review you did not verify. Show real command output.
5. Never expose secrets found during review in your report — say where it is, not what it is.

## Workflow

### 1. Run the pipeline

```bash
cd <cdk-project-dir>
<pm> run check      # format:check -> lint -> build -> test -> synth -> nag
```

If `check` does not exist, run the steps individually. Record each result exactly; a failing step is
a finding, not a reason to stop the review.

### 2. Look at what was synthesized

```bash
<pm> run synth                                   # cdk.out/*.template.json
npx cdk diff <stack> --profile <profile>         # read-only, needs credentials
```

Review the generated template and the diff, not just the TypeScript. Check for:

- resource deletion or replacement (`Resources ... destroy/replace` in the diff),
- IAM statements that widened,
- public exposure (open security groups, public buckets, `AuthorizationType: NONE`),
- encryption or retention that got weaker,
- networking changes,
- resources you did not expect from the change description.

### 3. Review the code

Security and IAM:

- wildcards in actions or resources, `AdministratorAccess`, broad managed policies, shared roles,
- secrets or account IDs in code, profile names hard-coded, `process.env` read inside constructs,
- overridden L2 secure defaults, public access, missing encryption, missing TLS enforcement,
- stateful resources without a removal policy or with an unintended `DESTROY`.

Design:

- stacks split for code size instead of a deployment boundary; constructs that wrap a single L2
  without adding anything,
- folders organised by AWS service instead of domain,
- L1 escape hatches without a comment or an assertion,
- construct IDs or physical names that changed (replacement risk),
- configuration duplicated across stacks instead of living in `lib/config`.

Tests:

- a stack without a snapshot test,
- generated, conditional, props-driven or security-relevant configuration without a fine-grained
  assertion,
- snapshots updated in the same change as a security-relevant template diff,
- skipped or deleted tests.

### 4. Report

Group findings by severity and be specific about location.

```text
CDK review: <scope>

Validation
  format:check PASS   lint PASS   build PASS   test PASS   synth PASS   nag FAIL (2 findings)

Blocking
  1. <title>  (<file>:<line> / <construct path>)
     Issue:           <what is wrong and why it matters>
     Recommended fix: <the change you would make>
     Alternatives:    <other viable options>
     Trade-offs:      <cost, effort, operational impact>

Should fix
  ...

Consider
  ...

Destructive change detected
  <resource>: <delete | replace>  — cause: <changed logical ID / physical name / key schema>
  Impact: <data loss, downtime>  Options: <keep ID, migrate data, accept>

Decisions needed from you
  - <question with the options>
```

Severity: **Blocking** = data loss, credential exposure, public exposure, privilege escalation, a
failing required check. **Should fix** = weaker-than-default security, missing test coverage of
generated behaviour, IAM broader than needed. **Consider** = design, readability, maintainability.

For every cdk-nag finding use rule, resource, finding, security impact, recommended fix,
alternatives, trade-offs — then ask. Never acknowledge or suppress a finding yourself. cdk-nag v3
reports at ERROR and WARNING level and interrupts synthesis; the `nag` script runs
`cdk synth --strict`, so a warning-level rule fails the pipeline too.

### 5. After the user decides

Implement exactly what was agreed, re-run `<pm> run check`, and show the new results including any
snapshot diff you updated and why.
